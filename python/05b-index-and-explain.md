# W3 补充：索引与 EXPLAIN

> **面试必考，而且是"一追问就露馅"的重灾区。**
> 这一节的目标不是背概念，是**你能亲手测出差距、看懂执行计划**。

---

## 0. 先看一眼差距（真实数据）

```
10 万行数据，按 email 查一条：

无索引：  200 ~ 400 ms   ← 全表扫描，逐行比对
有索引：  1 ~ 5 ms       ← B+ 树直接定位

差 50~100 倍。
```

**为什么会差这么多？** 因为没索引时，MySQL 只能**从头到尾读一遍**（全表扫描），10 万行就是 10 万次比较。有索引时，B+ 树三层就能定位到那一行。

---

## 1. 索引是什么

**一句话**：索引是**额外的、排好序的数据结构**，让你不用扫描全表就能找到目标行。

**类比**：书的目录页。

```
没有目录：想找"第 7 章" → 从第一页翻起，翻到 300 页
有目录：  看目录 → 直接跳到第 187 页
```

**代价**：

| 好处 | 代价 |
|---|---|
| 查询快 | 占磁盘空间（一般 10~20%） |
| | **写入变慢**（插入/更新/删除都要维护索引） |

**所以不是索引越多越好**——每加一个索引，写入就多一份开销。

---

## 2. B+ 树：为什么是它

| 数据结构 | 问题 |
|---|---|
| 哈希表 | 只能等值查询，**不支持范围查询**（`age > 20` 用不了） |
| 二叉搜索树 | 树太高，磁盘 IO 次数多 |
| 红黑树 | 同样太高 |
| **B+ 树** | **矮胖**，三层能存千万级数据；**叶子节点有序且相连**，天然支持范围查询 |

**B+ 树的三个关键特征**：

1. **矮胖**：一个节点存几百个 key，三层就能覆盖千万行 → **3 次磁盘 IO 定位**
2. **数据只在叶子节点**：非叶子节点只存索引，能存更多 key
3. **叶子节点用链表相连**：`WHERE age BETWEEN 20 AND 30` 只需找到起点，然后顺着链表扫

**面试标准答法**：

> "B+ 树矮胖，磁盘 IO 次数少；叶子节点有序且用链表连接，范围查询高效；而且数据都在叶子节点，单次 IO 能读到更多索引项。"

## 3. 聚簇索引 vs 二级索引（回表）

**InnoDB 的特点：数据和主键索引存在一起**，这叫**聚簇索引**。

```
主键索引（聚簇索引）：叶子节点直接存【整行数据】
二级索引（普通索引）：叶子节点存【索引列 + 主键值】
```

**所以按二级索引查询时，要"回表"：**

```sql
SELECT * FROM users WHERE email = 'a@b.com';
```

```
① 在 email 索引树上找到 a@b.com → 拿到主键 id = 12345
② 再用 id 去主键索引树查完整行      ← 这一步叫【回表】
```

**两次 B+ 树查找。**

**怎么避免回表？用覆盖索引：**

```sql
-- 只查索引列，不需要回表
SELECT email FROM users WHERE email = 'a@b.com';

-- 索引 (email, username) 上，这个查询也能覆盖
SELECT email, username FROM users WHERE email = 'a@b.com';
```

EXPLAIN 的 `Extra` 列会显示 **`Using index`** —— 这就是覆盖索引的标志。

## 4. 最左前缀原则

**联合索引 `(a, b, c)` 相当于建了三个索引**：

```
(a)
(a, b)
(a, b, c)
```

**能用的查询**：
```sql
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND c = 3          -- 只有 a 走索引，c 不走（跳过 b）
```

**不能用的**：
```sql
WHERE b = 2                    -- ❌ 没有 a，完全用不上
WHERE b = 2 AND c = 3          -- ❌
WHERE a = 1 AND c = 3          -- ⚠️ 只有 a 能用，c 退化为过滤
```

**记忆**：从左往右连续匹配，断了就停。

## 5. ⭐ 索引失效的五种情况（面试高频）

### ① 对索引列做运算或函数

```sql
-- ❌ 索引列被函数包裹
WHERE YEAR(created_at) = 2026
WHERE id + 1 = 100

-- ✅ 改成范围查询
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE id = 99
```

**⚠️ 实测修正（重要）**：这种情况下 `type` 不一定是 `ALL`，**可能是 `index`**。

| type | 扫的是什么 | 好坏 |
|---|---|---|
| `ALL` | 整张**表** | 差 |
| **`index`** | 整棵**索引树** | **也是差**（除非数据很少） |

因为优化器发现"索引里就有我要的列"（覆盖索引），于是扫索引树比回表划算——**但它仍然是"从头扫到尾"，`rows` 照样是 10 万**。

> **所以判断快慢不能只看 `type` 是不是 `ALL`，要看 `rows`。**
> `type=index` + `rows=99474` 和 `type=ALL` + `rows=99474` 一样慢。

### ② 隐式类型转换

```sql
-- phone 是 VARCHAR，但传了数字 → MySQL 会转成数字比较 → 失效
WHERE phone = 13800138000        -- ❌
WHERE phone = '13800138000'      -- ✅
```

**这是最隐蔽的一种**——代码里传了个 int 进来，悄悄就失效了。

### ③ 前导模糊匹配

```sql
WHERE name LIKE '%张三'          -- ❌ 无法用索引做范围定位
WHERE name LIKE '张三%'          -- ✅ 能用（左前缀确定）
```

**⚠️ 实测结果**：

| 写法 | type | rows | 说明 |
|---|---|---|---|
| `LIKE '%user50000%'` | `index` | **99474** | 扫整棵索引树，白扫 |
| `LIKE 'user50000%'` | `range` | **1** | ✅ 只扫 1 行，非常高效 |

**结论**：
- **前导 `%` 的模糊查询基本就是全扫**（不管 type 显示 ALL 还是 index，看 rows）
- **`字段%` 这种左前缀模糊，索引是真正生效的**，而且效率很高——很多人以为"LIKE 就不能用索引"，**这是错的**，只有前导 `%` 才失效

### ④ `OR` 连接了非索引列

```sql
-- 如果 age 没索引，整个查询都不走索引
WHERE email = 'a@b.com' OR age = 20
```

## 5.5 ⭐ 判断快慢的唯一标准：看 `rows`

以上所有"索引失效"的讨论，最后都归结为一个动作：

> **看 EXPLAIN 里的 `rows`。它才是"预估要扫多少行"。**

| `rows` | 含义 | 判断 |
|---|---|---|
| 1 ~ 10 | 索引精确定位 | ✅ 好 |
| 几十 ~ 几百 | 范围查询，正常 | ✅ 可接受 |
| **接近表总行数** | **等于全扫** | ❌ 索引白建了 |

**`type` 只是"访问方式的名字"，`rows` 才是"实际代价"。**

- `type=ALL` + `rows=100000` → 扫全表
- `type=index` + `rows=100000` → 扫全索引树
- **两者一样慢**，区别只是扫的对象不同

## 6. EXPLAIN：怎么看执行计划

> ⚠️ **MySQL 26 的版本差异（我踩到了）**
>
> 新版 `EXPLAIN` 默认返回**单列树形文本**，不再是你熟悉的 12 列表格：
>
> ```
> EXPLAIN
> -> Index lookup on perf_test using idx_email (email = '...')  (cost=0.35 rows=1)
> ```
>
> **想拿到经典表格（`type` / `key` / `rows` / `Extra`），必须显式指定：**
>
> ```sql
> EXPLAIN FORMAT=TRADITIONAL SELECT ...;      -- 经典 12 列 ⭐
> EXPLAIN FORMAT=JSON SELECT ...;             -- 详细 JSON
> EXPLAIN ANALYZE SELECT ...;                 -- 带真实耗时
> ```
>
> **面试和八股讲的都是 `type=ref` / `type=ALL` 这套，所以用 `TRADITIONAL`。**


```sql
EXPLAIN SELECT * FROM users WHERE email = 'a@b.com';
```

**重点看这四列**：

| 列 | 看什么 |
|---|---|
| **`type`** | 访问类型，**最重要** |
| **`key`** | 实际用了哪个索引（NULL = 没用索引） |
| **`rows`** | 预估扫描行数（越小越好） |
| **`Extra`** | 额外信息，看有没有 `Using filesort` / `Using temporary` |

### `type` 的好坏排序（从好到坏）

```
system > const > eq_ref > ref > range > index > ALL
                                              ↑ 最差：全表扫描
```

| type | 含义 | 典型场景 |
|---|---|---|
| **`const`** | 主键/唯一索引等值查询，最多一行 | `WHERE id = 1` |
| **`eq_ref`** | 联表时用主键 | JOIN |
| **`ref`** | 普通索引等值查询 | `WHERE email = 'x'` |
| **`range`** | 索引范围扫描 | `WHERE age > 20` |
| **`index`** | 扫整个索引树 | 覆盖索引但没过滤 |
| **`ALL`** | **全表扫描** ❌ | 没索引或索引失效 |

**面试答法**："我看到 type 是 ALL，说明走了全表扫描，rows 是 10 万，所以慢。"

### `Extra` 里要警惕的

| Extra | 含义 |
|---|---|
| `Using index` | ✅ **覆盖索引**，不用回表，好 |
| `Using where` | 在存储引擎返回后再过滤 |
| **`Using filesort`** | ⚠️ 额外排序，通常说明 `ORDER BY` 用不上索引 |
| **`Using temporary`** | ⚠️ 用了临时表，`GROUP BY` 常见，尽量优化掉 |

## 7. 什么该建索引

| 该建 | 不该建 |
|---|---|
| 频繁出现在 `WHERE` 的列 | 很少查询的列 |
| `ORDER BY` / `GROUP BY` 的列 | 区分度极低的列（如"性别"） |
| 外键列（JOIN 用） | 频繁更新的列（维护成本高） |
| 唯一性约束列 | 表很小（几百行，全表扫更快） |

**区分度** = `COUNT(DISTINCT col) / COUNT(*)`，越接近 1 越好。**性别（区分度 0.5）不适合建单列索引。**
